# Multi-Model Governance Framework (BP1–BP8)

**Status: Phase E, Stage C — real, tested, and partial.** This document describes exactly what
exists today. It does not describe a target state as if it were already built.

## What this is

A unified, cross-BP governance view built on top of Phase D's real MLflow registry/governance
machinery (`src/mlops/`), extended in Phase E Stage C to cover all 8 business processes instead
of BP1 alone — without duplicating or replacing any of Phase D's tested code, and without
duplicating `src/monitoring/model_registry.py`'s pre-existing, pre-Phase-D config aggregation
(which this framework reuses as one of its three real inputs).

## The three real inputs, and why there are exactly three

| Input | Source | What it tells you |
|---|---|---|
| Config evidence | `src/monitoring/model_registry.py` (pre-existing) | Each BP's own committed Gate 3+ champion identifier, problem type, and gate-confirmation status — read live from `configs/*.yaml`, never re-derived. |
| MLflow registration | `src/mlops/registry.py` (Phase D) | Whether a real MLflow model version exists for this BP, and whether one currently holds the `champion`/`challenger` alias. |
| On-disk artifact | `src/mlops/enterprise_status.py` (new, Stage C) | Whether a real trained artifact file is actually present under `models/<bp>/`, and its real SHA-256. |

`src/mlops/enterprise_status.py` composes these three into one `BPGovernanceStatus` record per
BP — it computes nothing new about model quality; it is honest aggregation, the same design
principle `model_registry.py` already established.

## Why BP1–BP8 are not governed by one schema

BP1–BP8 are eight structurally different kinds of problems:

| BP | Problem type | Governance-applicable (classifier threshold schema)? |
|---|---|---|
| BP1 | trained_classifier | Yes |
| BP2 | trained_classifier | Yes |
| BP3 | trained_classifier | Yes |
| BP4 | benchmark_pipeline | No — has its own lag-reference check (`configs/bp4_*.yaml`'s `gate4_population_mean_lag_reference`) |
| BP5 | association_reporting | No — has its own Gate 6 pytest-based governance (`gate6_pytest_all_passed` etc.) |
| BP6 | retrieval_strategy | No — governed by its own retrieval-benchmark champion strategy |
| BP7 | rule_engine | No — has its own real self-test + disparate-impact audit (`src/monitoring/fairness_monitor.py`) |
| BP8 | gold_layer_aggregation | No — never a modeling problem |

Forcing BP4–BP8 through a classifier-style scalar-threshold schema would be exactly the kind of
invented, ill-fitting governance this project's zero-fabrication standard rules out. Each of
those BPs already has its own real, structurally appropriate check elsewhere in this repository —
this framework does not replace those; it clearly flags `governance_applicable=False` for them
rather than fabricating a fit.

## Real governance thresholds (BP1–BP3)

Derived from each BP's own real, already-committed `configs/*.yaml` Gate 3 numbers (not
invented), set at a real margin below the historically achieved value:

| BP | Metric | Historical value | Governance threshold |
|---|---|---|---|
| BP1 | held_out_test_accuracy | 0.8224 | 0.80 |
| BP1 | held_out_test_f1_macro | 0.822 (reported identically to accuracy at this balance) | 0.78 |
| BP2 | held_out_test_f1_macro | 0.4559 | 0.43 |
| BP2 | held_out_test_accuracy | 0.7558 | 0.72 |
| BP3 | held_out_test_roc_auc | 0.9762 | 0.95 |
| BP3 | held_out_test_recall | 0.9424 | 0.90 |

BP3's `held_out_test_precision` (0.151 recorded) is deliberately **not** thresholded — at BP3's
real 1.29% positive-class rate, precision is intrinsically low and high-variance, and gating on
it would reject good models for a reason unrelated to real quality.

## Lifecycle states

Six named states (`src/mlops/governance.py`'s `LifecycleState` enum): `development`,
`validation`, `staging`, `production`, `deprecated`, `archived`. A BP's current state is
**derived from real evidence**, never asserted:

- **production** — a real MLflow version holds `champion` AND a real artifact file is present on disk.
- **staging** — a real MLflow version holds `champion` or `challenger`, but no on-disk artifact was confirmed.
- **validation** — no MLflow registration, but the BP's own config shows a real, confirmed Gate 3+ evaluation.
- **development** — neither of the above.
- **deprecated** / **archived** — valid values; no BP has reached either yet, so no automatic path produces them.

## What Stage C does not cover yet (see PHASE_E_IMPLEMENTATION_REPORT.md for the full roadmap)

Model-specific lifecycle *transitions* for BP2–BP8 (actually retraining and registering a real
BP2/BP3 model version, wiring promotion/rollback for them) are not part of this stage — Stage C
builds the structural capability (thresholds, lifecycle derivation, status reporting) that such a
future retraining run would plug into, without fabricating the registration itself. Production
monitoring, serving-layer unification, security hardening, release-gate automation, and
disaster-recovery testing (Phase E Sections 3–8) are separate, later stages.
